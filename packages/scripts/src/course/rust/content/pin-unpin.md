Last lesson said `Pin`'s whole job is refusing to hand out `&mut`. Now watch it fold immediately:

```rust
use std::pin::Pin;

fn tweak(s: Pin<&mut String>) {
    let plain: &mut String = s.get_mut();   // compiles fine
    plain.push_str(" (updated)");           // so does this
}
```

`get_mut` hands the plain `&mut String` straight back, no `unsafe` anywhere. Either last lesson was wrong, or something about `String` makes the refusal unnecessary. It is the second, and the something is a trait: `Unpin`.

## Most types cannot point into themselves

What made the delivery machine fragile was one specific feature: a field holding the address of another field. A `String` has nothing like that. Its pointer aims at a heap buffer, and from One owner per value you know what a `String` move does: the three-word header moves, the buffer stays put. The header does not care where it lives. Move it a thousand times and the pointer inside stays correct, because it never pointed at the header's own location in the first place.

`Unpin` is the name for that shrug. It is an auto trait, the same mechanism behind `Send` and `Sync`: the compiler implements it automatically for any type whose fields are all `Unpin`, which covers integers, `String`, `Vec`, your `Subscriber` struct, essentially every type you have ever defined. `Unpin` does not mean "cannot be moved". It means: **moving this value after it was pinned breaks nothing, so the pin contract asks nothing of it.**

For an `Unpin` type the doors reopen: `Pin::new(&mut value)` is safe, `get_mut` is safe, `Deref` and `DerefMut` pass through. `Pin<&mut T>` where `T: Unpin` is just `&mut T` with paperwork. Every restriction from last lesson carried an invisible clause: unless `T: Unpin`.

The `!Unpin` list a working developer actually meets has one entry: futures generated by `async fn` and `async` blocks. The compiler opts all of them out without checking whether each one really borrows across an await; even `async { 2 + 2 }` is `!Unpin`. Conservative, free, and it keeps the rule of thumb simple: async machines, assume pinning matters; everything else, assume it does not. (Hand-built `!Unpin` types exist, opting out via `std::marker::PhantomPinned`, but you meet those as a consumer of libraries, not in application code.)

## Why your code never says Pin

If pinning is load-bearing, why will the newsletter service contain no `Pin` at all? Because the contract is produced by machinery at both ends:

- At the root, the runtime pins. `tokio::spawn` moves your future into a heap-allocated task and polls it at that address until it completes; `block_on` pins the future it drives before the first poll.
- In the middle, `.await` pins transitively. A child future is a field inside the parent's machine, so when the parent is pinned the child is pinned too, and the compiler generates the projection that proves it.

Root pinned by tokio, every layer below pinned by `.await`: the whole tree runs under the contract while your source never names it. You consume pinning the way you consume the stack: constantly, invisibly.

One std impl ties this together and explains most `Pin` errors you will ever see:

```rust
impl<F: ?Sized + Future + Unpin> Future for &mut F { /* ... */ }
```

A `&mut` to a future is itself a future, but only when `F: Unpin`, because `poll` needs a `Pin<&mut F>`, and manufacturing one from a bare `&mut` is only safe when moving-after-pinning is harmless. Next lesson, this one bound produces a compiler error in the middle of the delivery worker.

## Predict, then verify

`async { 2 + 2 }` holds no references at all, let alone self-references. Is its future `Unpin`?

Answer: no. The compiler does not analyze which async bodies are actually self-referential; it marks every `async fn` and `async` block future `!Unpin` wholesale. The precise analysis would be fragile: adding one borrow across an await deep in a function body would silently change the trait of your public type. So the language chose the blunt rule. Assume every async machine is `!Unpin` and you will never be surprised.
